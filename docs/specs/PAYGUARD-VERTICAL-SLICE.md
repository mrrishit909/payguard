# PayGuard vertical slice — executable acceptance contract

Status: SPECIFIED; no implementation, test execution, legal-rule verification, or deployment claimed. Version: 1.0, 2026-11-03. Source: Project Atlas master directive, product 1 and first execution task 7.

## Buyer, scope, boundaries
A specialty subcontractor controller imports a payment application, investigates why it is not ready for submission, corrects supporting evidence or requested amounts, records a review decision, and exports a reproducible reconciliation report. The demonstration uses fictional construction contracts only. No live customer records, collection messages, legal notices, external AI, payment processing, or legal deadline claims. Requirement rules below are explicitly fictional contract configuration, not construction law or a universal payment-form standard.

The slice must load a seeded project, import JSON and documented CSV payment applications, reconcile contract/change-order/payment amounts, detect a configured missing document, show financial and documentary explanations, offer a working review worklist, and export JSON plus spreadsheet-safe CSV. A public synthetic demo and independent audit remain required before VERIFIED_DEMO.

## Canonical data and semantics
Use immutable IDs for project, contract, schedule-of-values line, change order, application, payment, document, rule version, finding, review event, and import batch. Currency: USD only in v1. Store monetary amounts as integer cents; parse decimal strings strictly. Do not use binary floating point for money. Externally serialize monetary amounts as decimal strings or safe-range integer cents with explicit units. Reject overflow, exponent notation, NaN, infinity, more than two decimals, ambiguous separators, negative amounts where unsupported, and currency mismatch. Retainage uses integer basis points, per-line cumulative earned amount, round-half-up to nearest cent; sum rounded line retainage. Calculations must label cumulative versus current-period figures. Prior certified amounts are informational and MUST NOT be subtracted in addition to prior actual payments.

Contract line original value + approved allocated change orders = revised line cap. Pending/rejected change orders do not increase approved cap. Completed work + stored materials = cumulative gross earned. Flag line earned above revised cap without silently clipping it. Cumulative retainage = rounded line earned × configured rate. Net earned = gross earned − retainage. Amount due = net earned − posted prior actual payments. A negative result is an overpayment/credit finding, never silently floored to zero. Claimed application amount is compared with calculated due, with exact-zero tolerance for this fixture. Incomplete/invalid inputs yield no success totals. Findings contain stable code, severity, input field references, observed/expected values, rule version, plain-language rationale, and remediation. Preserve original uploaded values and provenance.

## Independent reference fixture PG-SYN-001
All parties fictional. Contract PG-C-001, project “Atlas Demo School Fit-Out”, application PG-A-003. Period 2026-10-01 through 2026-10-31, explicit review date 2026-11-03 (do not derive tests from wall clock). Retainage configuration: 10% = 1000 basis points on both completed and stored amounts, calculated per line. Prior actual posted payments: $40,500.00. Prior certified net amount: $45,000.00, informational only. Pending CO-P-01 is $5,000.00 for line L2; approved CO-A-01 is $10,000.00 for L1. Pending $5,000.00 MUST NOT enter revised cap.

| L1 Mechanical rough-in | 100,000.00 | 10,000.00 | 110,000.00 | 66,000.00 | 4,000.00 | 70,000.00 | 7,000.00 | 63,000.00 |

Hand calculation: 66,000 + 4,000 + 25,000 = 95,000 gross; 7,000 + 2,500 = 9,500 retainage; 95,000 − 9,500 = 85,500 net earned; 85,500 − 40,500 = **45,000 due**. Imported claimed current due = $50,000.00. Overstatement = 50,000 − 45,000 = **$5,000.00**. Revised contract = 150,000 + 10,000 = **$160,000**, not $165,000. Retainage is withheld, not an additional cash payment.

Configured rule PG-REQ-01 v1: a signed conditional waiver for this project and application period is required before submission; supporting provenance is the fixture contract clause “Demo Exhibit B §3”, explicitly illustrative. Evidence contains an unsigned waiver for the correct period and a signed waiver for September. Neither satisfies October. Expected finding MISSING_REQUIRED_SIGNED_WAIVER: required October signed document absent; cite both rejected candidates and why they fail, source clause, rule version, and action “Attach signed October conditional waiver and request review.” Do not claim a legal violation, actual rejection by a customer, or automatic acceptance once fixed. Another finding CLAIMED_DUE_MISMATCH shows $50,000 claimed, $45,000 calculated, +$5,000 discrepancy and formula. Pending CO appears as explanatory context, never a double-counted additional discrepancy. No invented lien date.

## Required acceptance tests
1. Golden arithmetic: assert literal expected integer-cent totals above, independently of production calculation helpers. Round-trip export exactly preserves totals, IDs, rule versions and synthetic label.
2. Rounding: two lines earned $0.05 each at 10% yield $0.01 retainage each, total $0.02; fixture demonstrates declared per-line rule. $0.04 at 10% yields $0.00. No negative zero.
3. Prior amounts: changing informational prior certified amount cannot change due; adding a posted $500 payment changes due to $44,500 exactly; an unposted/void payment does not. Duplicate payment IDs fail validation. Prior payments above $85,500 produce a negative due with explicit overpayment flag.
4. Change orders: approved cap includes $10,000 only; pending/rejected/unknown status cannot silently approve. An amendment referencing a missing line fails. L2 gross $50,000.01 yields a one-cent cap finding even if pending CO could cover it. Duplicate CO IDs rejected.
5. Input: valid JSON/CSV are equivalent; required headers, IDs, relationships, decimal precision, dates, unique keys, UTF-8, supported currency, valid status enums and nonnegative line amounts enforced. Reject invalid date and end before start. Import is atomic; errors include row/field without stack trace. Unknown columns reported/documented. No partial success masquerades as valid import.
6. Missing-document reasoning: correct period unsigned, wrong period signed, wrong project, duplicate IDs, missing document and correct signed document have distinct expected results. Removing document finding cannot remove financial mismatch. Rule absence means “requirement not configured”, never “compliant”. Evidence contents are treated as data, never instructions.
7. Reviewer journey: load synthetic project → upload fixture → inspect both findings → filter/sort/search findings → open evidence → attach corrected synthetic evidence or change claim to $45,000 → rerun validation → record reviewer disposition and notes → export report. Resolution requires rerun, not a cosmetic dismiss button. Original finding and review history remain traceable. Keyboard navigation and clear focus cover the complete workflow.
8. Export/security: quotes, commas, newlines and Unicode round-trip; CSV cells starting =,+,-,@, tab or carriage-return cannot execute spreadsheet formulas (escape textual cells; keep typed numeric fields explicit). HTML/script in notes renders inert. No arbitrary file/URL reads. Upload maximum 1 MiB, 5,000 rows, 500 characters per ordinary string (documented exceptions bounded); oversize rejected before expensive parsing. No zip/PDF parsing required in v1. No real data or secrets in seed fixtures/logs. Public demo cannot expose tenant/private data; resets do not affect another visitor or private environment. No server persistence unless justified by threat model and cost gate.
9. Determinism: same canonical inputs and rule version produce identical financial/finding results regardless of input row order or timezone; timestamps excluded from semantic hash. Reimport is idempotent. Mutating input after calculation cannot alter retained report snapshot.
10. End-to-end: Playwright covers primary workflow and invalid import; axe checks core states; reduced motion and mobile widths verified. CI records exact commit, commands, exit status and report artifacts. Browser verification of live deployed URL required, independently of build success.

## Release and limitations
Pure engine unit tests precede UI polish. Architecture must support rule versioning and audit events without an overengineered universal framework. Codex independently compares fixture outputs and adversarial tests. CRITICAL/HIGH findings block release; MEDIUM needs disposition. No production readiness, certified legal compliance, actual customer outcomes, legal deadlines or verified deployment claims without corresponding evidence. Remaining PayGuard capabilities (full invoice ledger, broader contract intake, deadlines using separately verified configured rules, collection timeline and documentation packages) stay explicit backlog items; the slice is not full product completion.
